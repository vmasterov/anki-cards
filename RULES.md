# RULES.md — регламент составления карточек

## 1. Цель

База для постоянного изучения и поддержания знаний, а не для авральной
подготовки. Карточка должна **учить**, а не только проверять знания: краткий ответ
сверху, развёрнутая теория под спойлером.

Целевая роль: senior-фронтенд (React / Vue / Nuxt) плюс общая инженерная база.

## 2. Объём и пропорция

**Размер темы не фиксирован.** Тема считается закрытой, когда покрыт её
план подтем, а не когда набрано заданное число карточек. Git может уложиться
в 30 карточек, асинхронность JS или TCP потребуют 60–80.

**Размер партии** — 15–30 карточек за одну генерацию: одна подтема или
связный блок. Это не ограничение Anki, а удобство вычитки и импорта.

Пропорция считается по теме целиком, а не по партии:

- **~80% фактических** — «что делает», «что вернёт», «в чём разница»,
  команды и синтаксис;
- **~20% на понимание** — trade-offs, «когда вредно», разбор ошибочного
  подхода.

Внутри фактических держать три ступени: определение → поведение в конкретном
коде → типичный подвох.

## 3. Типы заметок и когда что

| Задача | Тип | Файл |
|---|---|---|
| «Что делает X», определение | AllInOne, QType 2 (sc) | `sc.csv` |
| Набор верных утверждений | AllInOne, QType 1 (mc) | `mc.csv` |
| 4 утверждения верно/неверно | AllInOne, QType 0 (kprim) | `kprim.csv` |
| Команда, синтаксис, флаг | Задание с пропусками | `cloze.csv` |
| Точное имя метода или ключевого слова | Простая (с вводом ответа) | `type.csv` |
| «Объясни», trade-offs, чек-лист | Простая | `basic.csv` |
| Схемы (OSI, IP-пакет, box model) | Скрытие части изображений | вручную в Anki |

**Правило одного типа:** один CSV-файл содержит ровно один тип заметки.
Смешивать нельзя — ограничение импорта Anki.

## 4. Формат файлов

Служебная шапка каждого CSV:

```
#separator:Semicolon
#html:true
#notetype:AllInOne (kprim, mc, sc)
#deck:Раздел::Тема
#tags column:12
```

Порядок полей AllInOne (11 колонок + теги = 12):

`Question; Title; QType; Q_1; Q_2; Q_3; Q_4; Q_5; Answers; Sources; Extra 1; tags`

- `Answers` — нули и единицы через пробел, строго по числу заполненных `Q_n`.
- Неиспользуемые `Q_n` остаются пустыми.
- `Title` — короткая подтема (2–3 слова), видна над вопросом.

Встроенные типы в коллекции пользователя называются по-русски, потому что
коллекция создавалась с русским интерфейсом. В `#notetype:` писать точно:
`Задание с пропусками`, `Простая`, `Простая (с вводом ответа)`. У всех трёх
по два поля, сопоставляются по порядку колонок, плюс колонка тегов —
`#tags column:3`.

**Экранирование:** точка с запятой внутри текста требует обрамления поля
двойными кавычками. Переносы строк внутри поля запрещены — только `<br>`.
Markdown Anki не понимает, разметка только HTML.

## 5. Формулировка вопроса

- **Атомарность:** одна карточка — один факт. Если в ответе два независимых
  утверждения, это две карточки.
- Вопрос самодостаточен: понятен без соседних карточек и без контекста чата.
- **Без отрицаний** в формулировке («какой из вариантов НЕ является») —
  провоцирует ошибки невнимательности, а не незнания.
- Код инлайн — в `<code>`, многострочный — в `<pre><code>`.
- Длина вопроса — до двух строк на экране телефона.

## 6. Правила вариантов ответа

- 4 варианта по умолчанию, максимум 5.
- **Дистракторы — реальные заблуждения**, а не выдуманная чепуха. Источник:
  типичные ошибки на собеседованиях и в коде.
- Варианты **сопоставимы по длине и грамматической форме**. Правильный ответ
  не должен быть самым длинным или самым аккуратно сформулированным — это
  главная утечка в формате выбора.
- Для `mc` — минимум два правильных варианта, иначе это sc.
- Для `kprim` — ровно 4 утверждения.

## 7. Пояснение (поле Extra 1)

Структура:

1. **Одна строка «почему именно так»** — видна сразу.
2. `<details><summary>Теория</summary>` — 3–6 строк механизма: что происходит
   под капотом, а не пересказ ответа другими словами. `</details>`
3. При необходимости — минимальный пример кода внутри спойлера.
4. Для сетевых и абстрактных тем — аналогия.

Поле `Sources` — ссылка на MDN, спецификацию, RFC или официальную документацию.

## 8. Теги

Четыре обязательных тега на карточку:

- тема: `js`, `net`, `css`, `react`…
- подтема: `closures`, `tcp`, `grid`…
- уровень: `lvl-core` или `lvl-senior`
- идентификатор: `id-js-basics-sc-001`

Идентификатор уникален, не переиспользуется после удаления карточки и служит
связкой с `registry.csv`.

Для версионно-зависимых тем добавляется `volatile` — такие карточки
пересматриваются раз в полгода.

## 9. Именование

- Папки и файлы — латиницей: `decks/net-transport/sc.csv`.
- Колоды в Anki — кириллицей, иерархия через `::`:
  `Сеть::Транспортный уровень`.
- Одна тема = одна папка = одна колода.

## 10. Запрещено

- Номера версий и свежие API в вопросах (устаревает быстрее, чем повторяется).
- Вопросы, где правильных записей ответа несколько, в формате type-in
  (`git commit -m` против `--message`).
- Перефразировки уже существующих вопросов — проверяется по `registry.csv`
  перед генерацией.
- Карточки-простыни: если ответ не умещается в экран телефона без прокрутки,
  тему надо разбить.

## 11. Процесс генерации партии

1. Прочитать `HANDOFF.md` и `registry.csv`.
2. Если у темы ещё нет плана подтем — составить его и записать в
   `HANDOFF.md`. Сгенерировать партию 15–30 карточек по одной подтеме.
3. Прогнать `tools/check.py`: число колонок, соответствие маски числу
   вариантов, дубли внутри партии и против реестра, запрещённые символы.
4. Записать файлы в `decks/<topic>/`.
5. Занести карточки в реестр: `python3 tools/register.py decks/<topic>`.
   Обновить статус и план подтем в `HANDOFF.md`.
6. Отчитаться: что сгенерировано, что проверено, что импортировать.

Импорт в Anki и коммит в git — за пользователем. При импорте включать
«Update existing notes», чтобы правки доезжали, а не двоились.

## 12. Ревизия

Карточка, помеченная Anki как leech (постоянно забывается), — сигнал плохой
формулировки, а не плохой памяти. Такие собираются по тегу и переписываются.

Карточки с тегом `volatile` пересматриваются раз в полгода на актуальность.
